# Meal logging database

`schema.ts` defines `meals`, `foods`, `mealItems`, the meal type enum, inferred
insert/select types, and Drizzle 1.0 `defineRelations` relations. `index.ts`
registers those relations with the existing Neon HTTP client.

UUIDs and creation timestamps are generated by PostgreSQL. `eatenAt` is required
and stored with a time zone; application code should group by the user's local
day. Quantities count food units and support three decimal places. Per-unit
nutrition supports two decimal places and remains a decimal string in Drizzle.
Null nutrition means unknown, while `"0.00"` means known zero.

`nutrition.ts` calculates consumed calories and macros from quantity and the
item's snapshots using exact scaled integer arithmetic. Results are decimal
strings with up to five decimal places. A missing nutrient produces a null item
value and a null meal total for that nutrient, with `isComplete: false`. Totals
are calculated on demand and are never stored.

## Migrations and verification

The CLI loads `.env*` files using Next.js's environment loader, including
`.env.local`, and retains the PostgreSQL dialect and `DATABASE_URL` configuration.

```sh
npm run db:generate  # Generate versioned SQL and its schema snapshot
npm run db:verify    # Apply migrations and test constraints in in-memory PostgreSQL
npm test            # Database tests plus exact nutrition calculation tests
npm run typecheck
npm run lint
```

Review the generated `drizzle/*/migration.sql` before applying it. Once
`DATABASE_URL` points to the intended development Neon database, run:

```sh
npm run db:migrate
```

Local tests use PGlite and the actual Drizzle migration runner. They do not read
`DATABASE_URL`, contact Neon, or persist test data. The migration is generated
and validated locally; it has not been applied to Neon.

## Contract for future server operations

- Derive `userId` from Clerk authentication, and filter every read by that user.
  Composite foreign keys prevent items from referencing another user's meal or
  food; they do not authenticate requests or filter reads.
- Keep one catalog food per normalized name per user, including archived foods.
  Names are normalized by `lower(btrim(name))` for uniqueness.
- Reject amount-specific catalog names. Log two apples as one item with quantity
  `"2"`; each food can appear only once per meal.
- When logging, copy the food's name and all four per-unit nutrition values into
  the corresponding item snapshots. Later catalog edits do not update snapshots.
  Snapshot copying belongs in the future authenticated write operation.
- Create a completed meal with at least one item in a single transaction. The
  schema permits an empty meal while future application code enforces completion.
- Archive referenced foods instead of deleting them. Food deletion is restricted
  while references exist; deleting a meal cascades to its items.

UI and CRUD endpoints are outside this change.
